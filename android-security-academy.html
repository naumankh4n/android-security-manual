📚 Android Fundamentals

Core concepts every Android security tester must understand.

📐 Android Architecture Layers

📦 What is an APK?

APK = Android Package Kit. It's a ZIP archive containing the compiled app, resources, and manifest. Think of it as Android's equivalent of .exe or .app.

APK Contents 
📦 app.apk
├── 📄 AndroidManifest.xml     ← Binary XML (app config)
├── 📁 META-INF/               ← Signatures & certificates
│   ├── CERT.RSA
│   ├── CERT.SF
│   └── MANIFEST.MF
├── 📁 classes.dex             ← Dalvik bytecode (compiled Java/Kotlin)
├── 📁 classes2.dex            ← Multi-dex (if app is large)
├── 📁 res/                    ← Resources (layouts, drawables, strings)
├── 📁 assets/                 ← Raw asset files (fonts, HTML, configs)
├── 📁 lib/                    ← Native libraries (.so files)
│   ├── arm64-v8a/
│   ├── armeabi-v7a/
│   └── x86_64/
└── 📄 resources.arsc          ← Compiled resources table

📋 AndroidManifest.xml — The Blueprint

The Manifest declares everything about the app: components, permissions, hardware features, and more.

AndroidManifest.xml 
<manifest package="com.example.app">

    <!-- Permissions the app requests -->
    <uses-permission android:name="android.permission.INTERNET"/>
    <uses-permission android:name="android.permission.CAMERA"/>

    <!-- App configuration -->
    <application
        android:allowBackup="true"           <-- ⚠️ Security: allows ADB backup
        android:usesCleartextTraffic="true" <-- ⚠️ Security: allows HTTP
        android:debuggable="false">          <-- Should be false in release!

        <!-- ⚠️ exported=true means other apps can launch this -->
        <activity android:name=".MainActivity"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN"/>
                <category android:name="android.intent.category.LAUNCHER"/>
            </intent-filter>
        </activity>

        <service android:name=".MyService"
            android:exported="true"/> <-- ⚠️ Check this!

        <receiver android:name=".MyReceiver"
            android:exported="true"/> <-- ⚠️ Check this!

        <provider android:name=".MyProvider"
            android:exported="true"
            android:authorities="com.example.provider"/> <-- ⚠️ Check this!

    </application>
</manifest>

🧩 The Four Android Components

1️⃣ Activity UI Screen

A single screen with a user interface. Every screen the user sees is an Activity (or Fragment within one).

Lifecycle: onCreate → onStart → onResume → onPause → onStop → onDestroy

Security concern: Exported Activities can be launched by other apps → bypass authentication, steal data

$ adb shell am start -n com.example/.SecretActivity
Starting: Intent { cmp=com.example/.SecretActivity }
⚠️ Launches activity from outside the app!

2️⃣ Service Background

Runs in background, no UI. Used for long-running operations (music, downloads, sync).

Types: Started Service, Bound Service, Foreground Service

Security concern: Exported Services can be started/bound by other apps → data theft, code execution

3️⃣ Broadcast Receiver Event Listener

Listens for system-wide broadcast announcements (boot complete, battery low, SMS received).

Security concern: Exported Receivers can receive spoofed broadcasts → trigger unintended actions

$ adb shell am broadcast -a com.example.CUSTOM_ACTION --es key "malicious"
Broadcasting: Intent { act=com.example.CUSTOM_ACTION (has extras) }

4️⃣ Content Provider Data Access

Manages shared app data (SQLite, files). Provides CRUD interface via content:// URIs.

Security concern: Exported Providers can leak data, allow SQL injection, path traversal

$ adb shell content query --uri content://com.example.provider/users
Row: 0 _id=1, name=admin, password=supersecret123

🔄 Component Communication Flow

🎯 What is an Intent?

An Intent is a messaging object used to request an action from another app component. It's the fundamental IPC mechanism on Android.

Intent TypeDescriptionSecurity Risk
ExplicitTargets a specific component by class nameLow — Intent is delivered to known recipient
ImplicitDeclares an action, system resolves which component handles itHigh — Intent hijacking, eavesdropping
PendingIntentToken given to foreign app; it executes with original app's permissionsCritical — Privilege escalation if mutable

📨 Intent Extras (Data Payload)

Key-value pairs attached to Intents. Apps use these to pass data between components.

Intent with Extras 
// Creating an Intent with extras
Intent intent = new Intent(this, ProfileActivity.class);
intent.putExtra("user_id", "12345");       // ⚠️ Trusted?
intent.putExtra("is_admin", true);        // ⚠️ Can be forged!
intent.putExtra("auth_token", "eyJhbG...");  // ⚠️ Sensitive in transit!
startActivity(intent);

⚠️ Risk Intent extras can be read by any receiver if sent via implicit intent. Never trust extras from external sources!

🔀 IPC (Inter-Process Communication) on Android

Android apps run in separate processes (sandboxed by UID). IPC mechanisms:

MechanismHow It WorksUsed By
IntentsAsynchronous messages via BinderActivities, Services, Receivers
Binder (AIDL)RPC-style interface definitionBound Services
ContentProviderURI-based data accessData sharing between apps
MessengerMessage queue on top of BinderSimple service communication

📝 What is Smali?

Smali is the human-readable assembly language for Android's Dalvik VM bytecode. When JADX can't decompile a method, you can read/modify the smali directly.

Smali Example 
# Java: boolean isAdmin = checkAdmin(user);
# Smali:
invoke-static {p1}, Lcom/example/Auth;->checkAdmin(Ljava/lang/String;)Z
move-result v0
if-eqz v0, :cond_not_admin   # Jump if false

# To bypass auth: change if-eqz to if-nez
# Or: always set v0 = 1 (true) before the check

apktool produces smali files. You can modify them and repack: apktool b output/ -o patched.apk

🧩 Component Vulnerabilities

Exploiting exported Activities, Services, Broadcast Receivers, and Content Providers.

🎯 Exported Activity Vulnerability

When android:exported="true" (or an intent-filter is declared), ANY app can launch the Activity.

🔴 Scenario: Bypass Login
  • Find exported Activity in Manifest: com.example.DashboardActivity
  • Check if it has auth checks (JADX review)
  • Launch directly: adb shell am start -n com.example/.DashboardActivity
  • If Dashboard loads without credentials → bypass confirmed
🔴 Scenario: Intent Extra Manipulation
  • Activity reads getIntent().getStringExtra("user_id")
  • Launch with modified extra: adb shell am start -n com.example/.ProfileActivity --es user_id "9999"
  • If you can view another user's profile → IDOR via Intent

📻 Broadcast Receiver Spoofing

An exported Receiver trusts broadcasts from anywhere. Attackers can forge them.

🔴 Scenario: Trigger Sensitive Action
  • Receiver ResetPasswordReceiver is exported
  • It resets password when receiving RESET_PASSWORD action
  • Spoof it: adb shell am broadcast -a com.example.RESET_PASSWORD --es email "victim@test.com"
  • Password reset triggered without authentication → critical

🗄️ Content Provider Exploitation

Exported Content Providers can leak data, be vulnerable to SQL injection, or path traversal.

TestCommand
Query dataadb shell content query --uri content://com.example.provider/users
Path traversaladb shell content read --uri content://com.example.provider/../../../etc/hosts
SQL injectionadb shell content query --uri "content://com.example.provider/users?--"
Insert dataadb shell content insert --uri content://com.example.provider/users --bind name:s:attacker

🔄 Intent Redirection

When an app takes an embedded Intent from incoming data and forwards it — attacker controls where it goes.

Vulnerable Pattern 
// Attacker sends Intent with an embedded Intent inside
Intent attackerIntent = new Intent();
attackerIntent.putExtra("forwarded_intent", maliciousEmbeddedIntent);
// Victim app blindly forwards it:
Parcelable extra = getIntent().getParcelableExtra("forwarded_intent");
startActivity((Intent) extra);  // ⚠️ Launches attacker's chosen component!

⚠️ PendingIntent Security

What: A token that lets a foreign app execute an Intent with YOUR app's identity/permissions.

Risk: If PendingIntent.FLAG_MUTABLE is set (Android 12+), the receiver can modify the Intent — changing the target component, adding extras, etc.

Secure vs Insecure 
// ✅ Secure (Android 12+):
PendingIntent.getActivity(ctx, 0, intent,
    PendingIntent.FLAG_IMMUTABLE);

// ⚠️ Insecure — receiver can modify:
PendingIntent.getActivity(ctx, 0, intent,
    PendingIntent.FLAG_MUTABLE);

🌐 Network Security

TLS, certificate pinning, Burp Suite setup, cleartext traffic analysis.

🔧 Burp Suite Setup for Android

1. Set Burp proxy listener (all interfaces, port 8080)
⬇
2. Export Burp CA cert → push to device
⬇
3. Install cert on device (Settings → Security → Install)
⬇
4. Configure WiFi proxy → Burp IP:8080
⬇
5. Traffic should appear!
$ adb push burp-cacert.der /sdcard/
$ adb shell settings put global http_proxy 192.168.1.100:8080
Proxy set. Now browse on device.

❌ Why HTTPS Traffic May NOT Appear

CauseSolution
Certificate PinningBypass with Frida/Objection scripts
Proxy not configuredCheck WiFi proxy or use adb reverse
Android 7+ — only system CAs trustedRoot + move cert to system store, or use Frida
Network Security Config blocks user CAsModify NSC in apktool, repack, or Frida patch
Non-HTTP protocolWebSockets, raw TCP, gRPC → use Wireshark/tcpdump
App uses custom SSL socket factoryHook with Frida to intercept

📌 Certificate Pinning

Apps "pin" a specific certificate or public key. They reject any other — including Burp's CA. This is a defense, not a vulnerability.

Pinning Implementation (OkHttp) 
CertificatePinner certPinner = new CertificatePinner.Builder()
    .add("api.example.com",
        "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build();

OkHttpClient client = new OkHttpClient.Builder()
    .certificatePinner(certPinner)
    .build();

💡 Note Bypassing pinning requires root + Frida, or patching the APK. The bypass itself is not a vuln — it just enables further testing.

$ frida -U -l bypass-pinning.js -f com.example.app
[+] Certificate pinning bypassed!

🔓 Cleartext Traffic & NSC

Network Security Config (NSC) is an XML file (res/xml/network_security_config.xml) that customizes TLS settings.

Network Security Config 
<network-security-config>
    <!-- ⚠️ Allows cleartext (HTTP) traffic -->
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="true">example.com</domain>
    </domain-config>

    <!-- ⚠️ Trusts user-installed CAs (debug config in production!) -->
    <base-config>
        <trust-anchors>
            <certificates src="user"/>
        </trust-anchors>
    </base-config>
</network-security-config>

Check in Manifest: android:networkSecurityConfig="@xml/network_security_config"

Hostname Verification: Ensures the certificate CN matches the hostname. Can be disabled with custom HostnameVerifier returning true for all. Check JADX for this.

⚠️ SharedPreferences Risks

Stores key-value pairs as plain XML. Not encrypted!

Insecure Storage Example 
// ⚠️ DON'T DO THIS:
SharedPreferences prefs = getSharedPreferences("auth", MODE_PRIVATE);
prefs.edit()
    .putString("access_token", "eyJhbGciOiJ...")
    .putString("user_password", "P@ssw0rd123")
    .putBoolean("is_admin", true)
    .apply();

// ✅ DO THIS (EncryptedSharedPreferences):
MasterKey masterKey = new MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
    .build();
SharedPreferences securePrefs = EncryptedSharedPreferences.create(
    context, "secure_auth", masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
);

🔐 Android Keystore

Hardware-backed key storage (Trusted Execution Environment). Keys never leave secure hardware.

Keystore Usage 
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
    "my_key_alias",
    KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT
)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true) // Requires biometric/PIN
    .build();

✅ Best Practice: Store auth tokens in EncryptedSharedPreferences with Keystore-backed keys, NOT in plain SharedPreferences.

🔐 Authentication & Authorization

JWT analysis, IDOR/BOLA, session management, client-side trust issues.

🎯 Auth vs Authz vs IDOR

ConceptQuestion It AnswersWhere to Test
Authentication"Who are you?"Login, biometric, MFA flows
Authorization"What can you do?"Role checks, access controls
IDOR/BOLA"Can you access object X as user Y?"API endpoints with resource IDs
🔴 IDOR Test: Change user_id in API request
  • Login as User A, capture profile API: GET /api/user/1234/profile
  • Change to User B's ID: GET /api/user/5678/profile
  • If you get User B's data → IDOR confirmed
  • Same for PATCH/PUT: try modifying another user's data

🔑 JWT Testing Checklist

$ # Decode JWT:
Header: {"alg":"RS256","typ":"JWT"}
Payload: {"sub":"1234","role":"user","exp":9999999999}
$ # Tests to perform:
1. Change alg:none → remove signature
2. Change role:user → role:admin
3. Change sub:1234 → sub:5678 (IDOR via JWT)
4. Set exp far in future (or past for testing)
5. Try HMAC key confusion (RS256→HS256)

⚠️ Critical Never trust role values from the mobile app (JWT payload, SharedPreferences, or Intent extras). Authorization MUST be enforced server-side.

🚫 What NOT to Trust (Client-Side)

Data SourceWhy It Can't Be Trusted
SharedPreferences role flagRoot → read/write any value
JWT payload (locally modified)Signature may not be validated properly server-side
Intent extras (is_admin)Attacker controls all extras from external Intents
Client-side biometric resultCan be bypassed with Frida
Local DB row for "user role"Root → SQLite modification
API response body cached locallyTampered to show fake "admin" UI

Golden Rule: The backend is the single source of truth. The mobile app is an untrusted client.

🔥 Interview Scenario Walkthroughs

Practice these out loud. These are the questions interviewers love.

🔴 Q118: You receive an APK. Walk me through your complete testing methodology.
  • Phase 1 — Recon: Run MobSF for automated scan. Review the report for high-level issues.
  • Phase 2 — Static Analysis: Decompile with JADX. Review AndroidManifest.xml for exported components, allowBackup, debuggable, cleartextTraffic. Search code for hardcoded secrets (API keys, tokens, passwords, private keys). Analyze crypto implementation. Map all deeplinks.
  • Phase 3 — Dynamic Analysis: Install on rooted device. Set up Burp intercept. Bypass certificate pinning if present. Exercise all app functionality while monitoring Burp + Logcat. Test API endpoints for IDOR. Test exported components with ADB/drozer.
  • Phase 4 — Storage: Pull app data directory. Check SharedPreferences, SQLite DBs, cache, temp files. Perform ADB backup if allowBackup=true.
  • Phase 5 — Runtime: Use Frida/Objection for runtime analysis. Hook auth functions. Bypass root detection if blocking. Monitor crypto operations.
  • Phase 6 — Report: Document findings with severity, proof of concept, and remediation.
🔴 Q119: Exported Activity — is it actually vulnerable?
  • Step 1: In JADX, check if the Activity validates the calling package (getCallingPackage()).
  • Step 2: Check if it requires a permission (via Manifest or checkCallingPermission()).
  • Step 3: Check if it reads Intent extras and uses them for auth decisions (user_id, role, token).
  • Step 4: Check if it performs sensitive actions (data access, settings change, navigation to protected screens).
  • Step 5: If no checks → launch it from another app/ADB. If it performs the action → vulnerable.
🔴 Q120: Exported Activity accepts user_id via Intent Extra — what to test?
  • Test IDOR: adb shell am start -n com.app/.ProfileActivity --es user_id "9999" — see if you can view another user's data.
  • Test privilege escalation: Check if modifying a role extra changes behavior.
  • Test injection: Pass special characters, SQL injection payloads, path traversal in the extra.
  • Test that the backend re-validates user_id — the mobile app should NEVER trust client-provided user IDs for auth.
🔴 Q121: Auth token in SharedPreferences — risk & remediation
  • Risk: Any app with root access (or ADB backup) can read the plain XML file and steal the token → account takeover.
  • Remediation: Use EncryptedSharedPreferences with Android Keystore-backed keys. Or use the Keystore directly. Never store tokens in plaintext.
  • Additional: Tokens should have short expiry, be refreshable, and be revocable server-side.
🔴 Q122: App doesn't show HTTPS traffic in Burp
  • Check 1: Is Burp proxy set correctly? (WiFi proxy or adb reverse)
  • Check 2: Is Burp CA installed as user cert? (Needs system cert on Android 7+)
  • Check 3: Certificate pinning? → Use Frida/Objection to bypass.
  • Check 4: Network Security Config blocking user CAs? → Patch or bypass.
  • Check 5: Non-HTTP traffic (WebSocket, raw TCP)? → Use Wireshark/tcpdump.
  • Check 6: App using custom trust manager? → Hook it with Frida.
🔴 Q125: No login bypass, but API lets you change another user's profile
  • This is IDOR (Insecure Direct Object Reference) / Broken Object Level Authorization (BOLA).
  • The app properly authenticates BUT fails to check: Does user X have permission to modify user Y's profile?
  • Vulnerability is server-side: the API endpoint doesn't validate resource ownership.
  • Test by changing resource IDs in API requests while authenticated as a different user.
🔴 Q126: Change role from user to admin — UI shows admin. Is it a vulnerability?
  • Maybe, but NOT automatically. If only the UI changes client-side (showing admin buttons) but the API still rejects admin operations → it's a UI bug, not a critical vuln.
  • BUT if the modified role value is sent to the backend and the backend TRUSTS it → critical authorization bypass.
  • Always check: does the backend independently determine the user's role, or does it trust what the client sends?
🔴 Q128: API key found inside APK — is it a vulnerability?
  • It depends on the key type:
  • Public API keys (Google Maps, Firebase config) → expected to be in client. Not a vulnerability.
  • Secret API keys (Stripe live secret, AWS secret key, private signing keys) → CRITICAL vulnerability. These should NEVER be in client code.
  • Check the key's scope: test what you can do with it. If it grants admin access to cloud resources → critical.
